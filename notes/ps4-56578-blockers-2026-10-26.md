## "STILL THERE? You have been returned to Orbit because you were inactive" - solved
- Every automated tutorial run left 15:34–15:40 after joining, whatever the Guardian was doing. The leave request (udt 14) carries the error hash `0x4CA36D9A` = `error.inactivity_timed_out` (errors are `{name, hash}` records, table at `0x26CAF40`, this one index 18).
- The world-controller state manager evaluates 38 prerequisites each frame (`0x792CD0`, dispatch `0x792ED0`); prerequisite **1** (`0x793A00`) fails with reason 18 when the local user's idle time (`0xB1BB00`: now − slot `+0x1B8`) exceeds the configured timeout (settings `+0x94` = 900 000 ms; `+0x98`/`+0x9C` 300 s, `+0xA0` 1 h, `+0xA4` 65 min by state).
- The activity tracker `0xB1B0E0` keeps, per user slot (`0x2803340 + user×0x140`): `+0x1A0` = last **button** change, `+0x1B0` = last **stick-quadrant** change, `+0x1B8` = last activity. In the world (state `0x24`) last activity = the **older** of the two, so stick input alone never counts. The walker only moved the sticks (and its one button press, a jump, was lost: see below), so the button time froze at spawn and the client left 15 minutes later.
- Fix: `d1-walk.py` presses square (reload, harmless with a full magazine) every 45 s, and `--keepalive SECONDS` holds a session open while idle. Verified live: square moves `+0x1A0`, the next stick move moves `+0x1B8`.
- Also fixed: `d1-pad.ps1` received comma-joined key lists from `powershell -File` as one string that named no key, so every multi-key call pressed nothing (the walker's back-off/side-step/jump recovery never happened). It now splits them.

## ✅ The Breach lights up and the barrier opens: prop authority (run `2026-10-26-agr-breach22`)
- The activation command reached the client (six copies of the exact image in memory), yet nothing happened: the Breach props (control, door lights, gating lights) had **no entity** (`component+0x390` = −1). Their state apply (`0x1238F0`) leaves creation to a per-frame creator (`0x123C70`) because their definition flags it (`def+0xA4`), and that creator spawns only if `0x108360(component)` says this machine may: the object's block (content `def+0x48`, or the local machine `0x345620` when ≥ 0x80) must be **held** in the world's authority masks: `world+0xA70` bit set and `world+0xA7C` (pending) bit clear (`0x2A1A80`).
- The authority applier (`0x2A1AB0`, udt 5 `has_sensor_block`) sets both bits when an entry's `seq` changes and clears both when the entry is `applied`. Our table was sent applied, so every block was taken and released in the same update. The client acknowledges a pending block for **its own machine** (`0x2A1440`: clears only `+0xA7C`, notifies listeners), which leaves it held. The local machine is 14 on the highway and **3 in The Breach**.
- Fix: `D1_AH_SENSOR_AUTHORITY=3,1,0` (machine, seq, applied=0; `SensorAuthority::all_to_with`). In the Breach block 3 becomes held, the three props get entities, the activation runs: **the room lights come on, the companion Ghost shows its blue core, the grey barrier opens**, the Guardian walks to the rifle and `trig_get_weapon` (`0x1D/35`) reports.
- The lit Breach renders washed out (white): the shadPS4 colour-LUT bug, now visible because there is light.
