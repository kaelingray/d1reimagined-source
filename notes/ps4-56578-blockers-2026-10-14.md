## ⭐ Blocker 1 narrowed: the client DOES create the loadout, from the wrong object tag (runs `weapslots`, `weapdefn`, `descwrite2`)

The chain, end to end:
1. **The body's inventory component** (code around 0x663000):
   - `+0x1E4` = current slot; `+0x1E8`/`+0x1EC`/`+0x1F0` = other slot indices;
   - `+0x1F4` = four weapon slots, 12 bytes each, handle first;
   - getters 0x6638C0 (slot handle), 0x663940 (current slot), 0x663A30;
   - writers 0x663FC0 (place handle) and 0x667750 (create + place).
   These are reached through member-function-pointer interface tables. The registry is 0xBF5670, which registers `{count, interface id, methods}` groups; ours is at 0x19AE370.
2. **The player-loadout method `0x668D80`** (interface entry at 0x19AE388), called once at spawn from 0x74044D. For each slot it reads the descriptor at `config + 0x368 + i*0x320`, takes **descriptor +0x00 as the weapon's object-definition tag**, and calls the creator `0x667800` → `0x308CA0` → sobject constructor. Then it places the result with 0x663FC0.
   The generic unit starting-weapon picker 0x663AE0 (a weighted list in the biped definition) also runs once and creates nothing.
3. **All three descriptors carry the same tag, `0x80A7E218`.** It is a real class `0x80800734` object-definition tag (`ps4_investment_assets_013f_5.pkg` entry 536, 34,644 B), but its sobject type (tag body +0xA6, i.e. definition +0x8E) is **8**, not a weapon (11). The player biped `0x80A6A06C` is the same class with type 9. Hence the three type-8 objects in the constructor log, the "weapon" slots holding non-weapons, and the switch action aborting.
   - Everything else in the descriptors is per item and correct: item SOIDs …0302/0303/0304, index 6/7/8, and per-item asset references such as 0x80A7739F (class 0x81063EDC), 0x80A765F7, 0x80A73BCC.
4. **Where the descriptor comes from.** At launch, `0x73D910(player, source)` (from the players system 0x9111C0/0x911850/0x911C50 via 0x73D8F0/0x73DAC0) copies a whole player-configuration struct with the copy constructor 0x104F3A0 into **`player + 0x1660`**. The write watch puts descriptor +0x00 at 0x104F4FB/0x104F5C7. The source struct already holds `0x80A7E218`. It is empty at orbit.

So the bug is data: the player configuration's per-weapon object tag resolves to a default instead of each weapon's own world-object tag. The peer-roster equipment elements we serve start with **16 zero bytes** before the item SOID. The most likely home for the real per-item object tag is there, or in the item instance (family 4/3) / definition fields the configuration builder reads.

Next:
- Find the configuration builder (where `source + 0x368 + i*0x320 + 0` is written; exec-log rsi at 0x104F3A0 to get the source address, then write-watch it), and what it reads to choose the tag.

### The intermittent world-loading crash (14 Oct, later)

### ⭐ Blocker 2 root cause: our Activity Host re-granted live entity indices on every state refresh (runs `reserve`, `slots`, `refreshfix`)

- **The slot pool** is the 0x3000-bit free mask at `db+0x120B8`:

  - Bits come back only through `0xB53A91` (one slot, on free) and `0xB53BB0` (bulk).

- **Where the bulk mask comes from.**
  - `0xBB57F0` feeds `0xB53BB0` with the inbox at `ac+0x5EA8` (`0x29BD90`), once per replication db, then zeroes the inbox (`0x298DB0`).

  - So **udt 0 is a delta**: every bit we send becomes a free slot, live or not.
