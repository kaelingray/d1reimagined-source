## 1. How to read this binary at all

Three facts that cost time before they were written down:

1. **A linear capstone sweep desyncs on the first data island and then silently stops.** Every
   "0 references found" from a whole-image sweep is a lie. Anchor on the enclosing prologue
   (`55 48 89 e5` = `push rbp; mov rbp,rsp`) and disassemble *forward*.
2. **Globals are reached RIP-relative.** `lea rax,[rip+disp32]` - so a literal-qword grep for an
   address finds nothing. Resolve as `next_instruction_va + disp32`.
3. **Bungie uses self-relative pointers everywhere.** The idiom is

   ```asm
   lea rdx, [rax + 8]
   add rdx, qword ptr [rax + 8]      ; rdx = (rax+8) + *(rax+8)
   ```

   i.e. *"the field holds the distance from its own address to the target."* A zero in such a field
   means NULL, not offset-zero. This appears in content tables, object arrays and schema records
   alike; misreading one as an absolute pointer produces plausible garbage rather than a fault.

### 1.1 The tag-handle → package-block resolver idiom `[C]`

This exact sequence means *"resolve a 32-bit content tag handle to its bytes in a loaded package"*.
Recognise it on sight; it marks the boundary between **code** and **shipped content**:

```asm
mov  edx, dword ptr [rdi]        ; the 32-bit tag handle
sar  eax, 0xd                    ; handle >> 13  -> block selector
shr  esi, 0x12
or   esi, 0x3ff
and  esi, eax
shl  rsi, 6                      ; * 0x40  -> block descriptor stride
mov  rcx, qword ptr [rax+rsi+0x10]   ; block base
movsxd rdi, dword ptr [rax+rsi+0x34] ; block mask
and  edx, 0x1fff                 ; handle & 0x1FFF -> element index within block
imul edx, dword ptr [rax+rsi+0x30]   ; * element stride
```

So a tag handle is `[block:19 | index:13]`, and `+0x30`/`+0x34` of the block descriptor are the
element **stride** and a mask. **Anything reached this way lives in `packages/`, not in the eboot.**

## 2. The prologue / veteran gate - SOLVED, and it was not where we were looking

**Claim under test (from `historicaldocs/design/rsat-character-object.md` §9):** the prologue sentinel reads
`+0x18` of *"a resolved character record"*, and the open task was to trace it back to a field of the
`0xA80` QueueZ character object.

**Result: it is not a field of the character object at all.** `[C]`

The chain, end to end:

| vaddr | what it is |
|---|---|
| `0x79F9F0` | **substage selector** - decides which prologue substage runs |
| `0x574220` | `get_thing(4)` - returns an object or NULL |
| `0x2646D0` | `index_of(object)` → **u16**, `0xFFFF` when not found |
| `0x79FAE0` | **prologue handler** - 5-case jump table on `[state+0x30]` |
| `0x548440` | `return *(void**)0x26A0910` - a global singleton |
| `0x548860` | `(rax, rdx) = resolve(singleton, u16 index)` |
| `0x5488E0` | tag-resolves the **content table**, caches it at `0x26A0920` |

### 2.1 The selector `0x79F9F0` `[C]`

```asm
079fa43  mov   word ptr [rbx + 0x34], 0xffff   ; default: NONE
079fa49  mov   edi, 4
079fa4e  call  0x574220                        ; -> object, or NULL
079fa53  test  rax, rax
079fa56  je    0x79fa66                        ; NULL -> keep 0xFFFF
079fa5b  call  0x2646d0                        ; -> ax = u16 index
079fa60  mov   word ptr [rbx + 0x34], ax
079fa6a  cmp   ax, -1
079fa6e  sete  al
079fa74  lea   eax, [rax + rax*4]              ; 0 or 5
079fa77  mov   dword ptr [rbx + 0x30], eax     ; substage
```

So the state record carries **`+0x34` = u16 index (`0xFFFF` = none)** and
**`+0x30` = substage**, and substage is `5` exactly when the index is absent, `0` otherwise.

### 2.2 The handler `0x79FAE0` `[C]`

Jump table base `0x79FEB8`, five entries, `cmp rax,4 / ja 0x79FE89`:

| substage | target |
|---:|---|
| 0 | `0x79FB1F` - the sentinel comparison |
| 1 | `0x79FB4C` |
| 2 | `0x79FB66` |
| 3 | `0x79FBE6` |
| 4 | `0x79FC22` |
| **5** | falls to `0x79FE89` (out of range - the `ja` default) |

⚠ **Substage 5 is deliberately out of the table's range.** "No index" is not a case; it exits.

### 2.3 The sentinel itself `[C]`

```asm
079fb1f  call  0x548440                     ; rdi = *(void**)0x26A0910
079fb24  movzx esi, word ptr [r14 + 0x34]   ; the u16 index from §2.1
079fb2c  call  0x548860
079fb31  mov   eax, dword ptr [rdx + 0x18]
079fb34  cmp   eax, 0x811c9dc5              ; the FNV offset basis = Destiny's NULL hash
                                            ; ⚠ FNV-1 and FNV-1a SHARE this basis, and this
                                            ; client's hash is FNV-1 (THE-CHAIN §4). Do not read
                                            ; this constant as evidence for FNV-1a - it is not.
079fb39  jne   0x79fca5                     ; NOT null  -> the other branch
079fb3f  mov   dword ptr [r14 + 0x30], 4    ; IS null   -> substage 4
```

### 2.4 Why `rdx` is content, not a character object `[C]`

`0x548860` returns **two** values - `rax` from a virtual call, and `rdx` from a table walk:

```asm
0548871  call  0x25c9a0                     ; -> r12, a manager singleton
054887c  call  0x5488e0                     ; -> rax, the CONTENT TABLE
0548885  movsxd rdx, dword ptr [rax]        ; table.count at +0x00
054888b  cmp   rdx, rcx                     ; bounds-check the index
0548893  jbe   0x5488a2                     ;   out of range -> return NULL in rdx
0548895  lea   rdx, [rax + 8]
0548899  add   rdx, qword ptr [rax + 8]     ; self-relative array base (§1)
054889d  lea   rbx, [rdx + rcx*8 + 0x10]    ; element = base + index*8 + 0x10
05488a9  mov   esi, r15d
05488ac  call  qword ptr [rax + 0x328]      ; -> RAX (a live object; separate answer)
05488b7  mov   rcx, qword ptr [rbx]
05488bf  add   rcx, rbx                     ; self-relative again -> the record
05488c5  mov   rdx, r14                     ; RDX = the content record
```

and `0x5488E0` reaches its table through the §1.1 tag-handle resolver, caching the result at
global `0x26A0920`.

### 2.6 The prologue SKIPS ITSELF when no record is supplied `[C]` / `[I]`

Recall §2.2: the substage is `5` exactly when the u16 index is `0xFFFF`, and §2.2's jump table only
covers `0..4`. That is not an oversight:

```asm
079fb0f  lea   rcx, [rip + 0x3a2]      ; jump table @ 0x79FEB8
079fb05  cmp   rax, 4
079fb09  ja    0x79fe89                ; substage 5 lands HERE
...
079fb47  jmp   0x79fe93                ; <- every IN-RANGE substage skips past 0x79FE89
...
079fe89  mov   edi, 0x19               ; 0x19 = 25 = `cleanup`
079fe8e  call  0x782710                ; request that state transition
079fe93  <epilogue>
```

**Substage 5 is the only branch that requests a state transition at all**, and it requests
`cleanup` - the state immediately before `setup:orbit_loading`. `[C]`

`0x782710(state)` tail-calls `0x782720(state, reason = 0, context = NULL)`; the null context resolves
to the literal `'none'` at `0x16075AA`, matching the `Context []` field in the client's own
`KTOBUCKET: STATE_CHANGE_REASON` log line. Reason `0` is a **non-error** reason - `0x782720` does
`cmp r13d, 0x10 / setb` and `cmp r13d, -1 / sete`, separating a small low class from the 260 `error.*`
reasons, which cannot fit below `0x10`. `[I]` - I did not pin reason `0` to the literal
`normal_flow`; the string is written into a runtime table by an initializer at `0x78401F` and the
disassembly around it desynced. Not chased further because it does not change the conclusion.

⇒ **We do not need to *do* anything to skip the prologue.** The index comes from `0x574220(4)` →
`0x2646D0`, and `0x574220` looks up **family 4 / type 4** - an object we have never sent. Absent that
object the index stays `0xFFFF`, substage is 5, and the handler walks itself to `cleanup` → orbit.

⚠ **CONTESTED 2026-08-11 ⇒ `prologue-and-bucket-unlock-gate.md`.** A later corpus crawl reads the

(`grants-and-unlocks.md` §2.5), with **no family-4/4 dependency** - the prologue would then be gated

⚠ `[U]` **Unverified live.** No run has reached state 24 yet - `character:signin` (23) is still

## 4. RSAT schema records - how to find any object's wire schema `[C]`

A schema record is followed by its descriptor. Both carry the same decoded object size, which makes
a tight signature.

> ⚠ **CORRECTED 2026-08-07 - my first reading of this table put the record base 8 bytes too high.**
> I read the *checksum* as `+0x00`. It is `+0x08` **of the pointer the code actually holds**:
> `0x56B6F8` resolves a schema tag and reads `[rsi+8]` to compare against the wire `instance_type`.
> Corroborated independently: the `u64` at the true base equals `end_of_fields - (base+8)` - the
> record's own length - for **1688/1688** records.
> ⇒ The record addresses I published (`0x139ADD8`, `0x1350758`, …) are each **8 too high**; the true
> bases are `0x139ADD0`, `0x1350750`, `0x12FA3F0`, `0x1304800`.
> **Nothing downstream changed**, which is exactly why this went unnoticed: the descriptor and field
> offsets are relative and were correct, so both lanes produced identical field tables. It was a
> labelling error, not a decoding one - but a labelling error is how the next person mis-seeks.
> (My draft also claimed `+0x18` was the decoded size. That is wrong under **either** base;
> `base+0x18` is the constant `8`.)

```
record base (what the code holds)
        +0x00 u64  the record's own byte length
        +0x08 u32  instance checksum   <-- the QueueZ `instance_type` on the wire
        +0x0C u32  zero
        +0x10 u32  class tag  (0x80xxxxxx)
        +0x14 u32  decoded object size
        +0x18 u32  constant 8
desc anchor = base + 0x50          (tags 0x80800050 / 0x8080010a)
        +0x08 u32  field count      (i.e. base+0x58)
        +0x10 u32  self tag         (i.e. base+0x60)
fields at desc_anchor + 0x30, stride 0x28:
        +0x00 start bit
        +0x08 flags        0x106 = primitive · 0x101 = child schema · 0x104/0x001/0x003 also seen
        +0x0C child tag    (0xFFFFFFFF = none)
        +0x10 BIAS         (0x80 for the u8 identity fields, 0x8000 for u16 leaves)
        +0x20/+0x24 tails  <-- NOT C offsets (rsat-character-object.md §10.1)
anchor+0x20 element count (non-zero => fixed array) · anchor+0x28 element stride
```

⚠ `anchor+0x1C` looks like the RSAT dirty-field span and is right for the four QueueZ objects, but
reads `0` for most *message* schemas whose children plainly carry bits. **Do not use it as a general
span field** - see `historicaldocs/design/message-catalogue.md`, which deliberately omits that column rather than
publish a confidently wrong one.

**Positive control:** the character record reproduces `rsat-character-object.md` §4 exactly -
6 fields, span `0x2C0` = 704 bits, children `808017FC / 8080181A / 80801755 / 80801855 / 80801923`. ✔

> An earlier version of this scan used a looser shape and **missed the roster entirely** while its
> control still passed on the other three. That is ATLAS §4.2b in the wild: a passing control proves
> the instrument, not the coverage. The fix was to require the record/descriptor size agreement.

### 4.2 The roster descriptor, in full `[C]`

0x139AE20   desc_tag 0x80801951   4 fields   span 4 bits
  [0] start=0x000  flags=0x106  child=none        tail=0x08/0x08   <- 64-bit SOID
  [1] start=0x001  flags=0x101  child=0x80804621  tail=0x60/0x60

## 5.1 The character-selection card builder `0xA110F0` - SOLVED `[C]`

It reads the character SOID list out of the **account** object (family 4 / type 0), *not* the
roster:

```asm
0a111fc  call 0x56ca70                          ; (family 4, type 0) -> the ACCOUNT object
0a11201  mov  rbx, rax
0a11204  mov  qword ptr [rbp - 0x738], rbx
0a112cd  cmp  dword ptr [rbx + 8], 0
0a112d1  jle  0xa116bb                          ; count <= 0  ->  build ZERO cards
0a112f0  mov  rax, qword ptr [rbx + r12*8 + 0x10]   ; SOID = array[i]
0a1132b  call 0x56ca70                          ; (family 3, type 1) -> that character
0a11336  je   0xa116a0                          ; missing -> skip this card
0a116a3  mov  rbx, qword ptr [rbp - 0x738]      ; back edge reloads the SAME account object
```

`rbx` is callee-saved and reloaded from one stack slot, so the indexed object is unambiguously the
account. Account field `[1]` and roster field `[1]` share the schema child `0x80804621` =
`{ u4 count @+0x00 ; u64 storage[10] @+0x08 }`, so **both** objects are
`{ +0x00 soid, +0x08 count, +0x10 u64[] }` - two lists, two readers:

| list | reader | decides |
|---|---|---|
| roster (family-3 root) | `0x78C9F0` | CREATION vs SELECTION |
| account (family 4/0) | `0xA110F0` | how many cards get built |

Full write-up and the wire consequence: `historicaldocs/design/character-and-orbit.md` §26.66-§26.68.

## §7 - THE ui_stage SUBSTAGE TABLE: every `ENUM(n)` in every log, by name `[C]`

The client logs `world_controller:ui_stage: Substage goal changed from 'ENUM(a)' to 'ENUM(b)'`
thousands of times per run and **never prints the name**. Until now every `ENUM(n)` in every artifact
in this project was an opaque integer. It is a plain string table at vaddr **`0x164993F`**, and the
mapping is **`name_index = ENUM(n) + 10`**.

### The control

Offset 10 is not a guess. Three substages name their own state exactly, and the `profile_setup`
triple resolves to the three screens the operator has described from the chair:

| state | substage | resolves to |
|---|---|---|
| `bootflow:bap_signin` | `ENUM(19)` | **bootflow bap signin** ✔ self-match |
| `bootflow:investment_signin` | `ENUM(20)` | **bootflow investment signin** ✔ self-match |
| `bootflow:prepare_for_orbit` | `ENUM(25)` | **bootflow prepare for orbit** ✔ self-match |
| `bootflow:profile_setup` | `ENUM(22)`→`(21)`→`(23)` | screen bounds → **brightness** → subtitles ✔ |
| `character:signin` | `ENUM(27)` | **character selection** ✔ |

Offsets 9 and 11 score 0/21 and 1/21 self-matches respectively; offset 10 scores 3/21. ⚠ The other
